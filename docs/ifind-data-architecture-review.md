# iFinD 数据中心架构方案专家评审

## 总体评价：可行（有风险需控制）

该方案在架构设计上**基本可行**，但存在几个需要重点关注的技术风险。建议在实施前先解决关键风险点，分阶段迭代。

---

## 关键问题清单（按严重程度排序）

### 🔴 严重风险

#### 1. iFinD API 调用频率限制未明确
- **问题**：方案中 5200+ 只股票每 5 分钟调用一次实时快照，但未说明 iFinD API 的实际限流策略
- **风险**：根据现有代码 `datasource.py:276` 的冷却逻辑，-9 错误（会话超限）会触发 2 小时冷却
- **影响**：可能导致整个调度器瘫痪，所有数据更新中断
- **建议**：在方案中明确 iFinD 的 API 限流策略（每日调用上限、并发限制），并设计降级方案

#### 2. SQLite 并发写入瓶颈
- **问题**：5200+ 只股票 × 78 次/天 = 40 万+ 条写入，SQLite 在高并发写入时性能急剧下降
- **风险**：WAL 模式虽支持并发读写，但写入仍需串行化；高频写入会导致锁等待
- **影响**：盘中 5 分钟一次的批量写入可能超时，影响数据实时性
- **建议**：
  - 考虑使用 PostgreSQL 或 DuckDB 替代 SQLite
  - 或采用内存写入 + 批量落库策略（每 5 分钟攒一批，一次性写入）

#### 3. 调度器与 Streamlit 进程隔离问题
- **问题**：方案提出新增 `lh-scheduler` 容器，但现有调度器 `scheduler.py` 是嵌入在 Streamlit 进程内的
- **风险**：两个调度器可能产生冲突（重复执行、状态不一致）
- **影响**：数据更新混乱、任务重复执行
- **建议**：明确迁移策略——是替换现有调度器还是并存？需要状态迁移方案

### 🟡 中等风险

#### 4. 数据一致性保障不足
- **问题**：方案提到使用 `INSERT OR REPLACE` 避免部分写入，但未考虑：
  - 批量写入中途失败如何回滚？
  - 多个定时任务同时操作同一张表如何避免冲突？
- **风险**：数据不一致可能导致页面展示错误数据
- **建议**：增加事务边界控制和写入锁机制

#### 5. 实时数据字段映射遗漏
- **问题**：方案中 `ifind_realtime` 表缺少一些关键字段：
  - `bid1/ask1`（买卖一档）
  - `limit_up/limit_down`（涨跌停价）
  - `avg_price`（均价）
- **风险**：页面展示时需要这些字段，缺失会导致功能降级
- **建议**：补充完整字段，参考现有 `quote_snapshots` 表结构

#### 6. 首次部署时间估算不足
- **问题**：方案估算磁盘空间 <200MB，但未估算首次拉取 7 天历史数据的时间
- **风险**：5200 只股票 × 7 天日线 = 36400 条数据，按现有 `_ths_fetch_daily` 实现（逐只抓取），可能需要 30-60 分钟
- **影响**：首次部署体验差，用户可能误以为系统故障
- **建议**：使用批量接口（如 `THS_HQ` 支持多只股票同时查询）优化首次拉取

### 🟢 低风险/可优化

#### 7. 运维复杂度增加
- **问题**：新增 `lh-scheduler` 容器意味着：
  - 需要维护两个容器的日志
  - 需要处理容器间通信
  - 需要监控调度器状态
- **建议**：考虑使用 Docker Compose 的 `depends_on` 和共享网络，简化运维

#### 8. 数据保留策略未实现清理机制
- **问题**：方案提到保留 7/15/30 天，但未说明如何清理过期数据
- **风险**：磁盘空间虽估算 <200MB，但长期运行可能累积
- **建议**：在调度器中增加定时清理任务（如每日凌晨清理过期数据）

## 改进建议清单

### 架构层面

1. **引入消息队列解耦**
   - 调度器只负责触发，实际数据获取由 worker 执行
   - 好处：失败任务可重试、负载均衡、状态追踪

2. **增加数据质量校验层**
   - 每次写入前校验数据完整性（非空、格式、范围）
   - 异常数据标记而非丢弃，便于人工排查

3. **设计降级策略**
   - iFinD API 不可用时，自动切换到备用数据源（如腾讯行情 `qt.gtimg.cn`）
   - 现有代码已有腾讯通道（`get_batch_snapshots`），可复用

### 性能层面

4. **批量写入优化**
   - 将 5 分钟一次的 5200 条写入改为批量事务
   - 使用 `executemany` 而非逐条 `execute`

5. **索引优化**
   - 为 `ifind_realtime` 表添加 `(code, datetime)` 复合索引
   - 为 `market_daily` 表添加 `(code, date)` 索引

6. **内存缓存策略**
   - 对高频查询（如最新快照）使用内存缓存
   - 减少数据库压力

### 运维层面

7. **健康检查机制**
   - 调度器暴露 `/health` 端点
   - 监控任务执行时间、成功率、失败原因

8. **告警通知**
   - 任务失败时发送通知（邮件/Webhook）
   - 现有方案提到阶段 2 实现，建议提前规划

9. **日志标准化**
   - 统一日志格式，便于后续分析
   - 记录每次 API 调用的耗时、返回码

## 风险点

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| iFinD API 限流导致任务失败 | 高 | 高 | 设计退避重试机制，监控调用频率 |
| SQLite 写入锁等待超时 | 中 | 高 | 批量写入，考虑升级到 PostgreSQL |
| 调度器状态丢失（容器重启） | 中 | 中 | 状态持久化到文件/数据库 |
| 首次部署拉取超时 | 高 | 低 | 使用批量接口，提供进度条 |
| 数据字段变更（iFinD SDK 升级） | 低 | 高 | 字段映射表可配置化 |

## 替代方案

### 方案 A：保持现有架构，优化调用方式
- **描述**：不新增容器，继续在 Streamlit 进程内调度，但优化数据获取逻辑
- **优点**：架构简单，运维成本低
- **缺点**：页面关闭后调度停止，数据更新不及时
- **适用场景**：个人使用，对实时性要求不高

### 方案 B：使用 Redis + Celery 替代 SQLite + APScheduler
- **描述**：用 Redis 做消息队列和缓存，Celery 做任务调度
- **优点**：高并发、任务重试、状态追踪
- **缺点**：运维复杂度高，需要额外服务
- **适用场景**：团队使用，对可靠性要求高

### 方案 C：使用 DuckDB 替代 SQLite
- **描述**：DuckDB 是专为分析设计的嵌入式数据库，支持更好的并发读写
- **优点**：分析查询更快，支持列式存储
- **缺点**：生态不如 SQLite 成熟，需要迁移成本
- **适用场景**：数据分析为主，查询复杂度高

### 方案 D：使用 PostgreSQL（推荐长期方案）
- **描述**：使用 PostgreSQL 作为主数据库
- **优点**：支持高并发、事务、JSON 字段、全文搜索
- **缺点**：运维复杂度高，需要额外容器
- **适用场景**：生产环境，多用户并发访问

## 实施建议

### 阶段 1（1-2 天）：MVP 验证
1. 仅实现 `ifind_stocklist` 和 `market_daily` 的定时更新
2. 页面改造为只读数据库
3. 验证 iFinD API 调用频率限制
4. 测试 SQLite 在当前负载下的性能

### 阶段 2（3-5 天）：核心功能
1. 实现 `ifind_realtime` 表和 5 分钟写入
2. 增加数据清理机制
3. 实现首次部署自动拉取
4. 增加健康检查和日志

### 阶段 3（1 周）：生产化
1. 增加告警通知
2. 性能优化（批量写入、索引优化）
3. 降级策略实现
4. 文档完善

---

## 结论

该方案**整体可行**，但需要：
1. 先验证 iFinD API 的实际限流策略
2. 评估 SQLite 在高频写入下的性能
3. 明确与现有调度器的迁移关系
4. 分阶段实施，降低风险

建议在正式实施前，先用 1 天时间做技术验证（Proof of Concept），确认关键风险点可控后再全面铺开。
